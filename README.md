# 사과게임 인공지능

10×17 판의 숫자 사과(1~9)를 드래그해 **합이 10인 직사각형**을 지우는 사과게임을 자동으로 푸는 프로젝트.
강화학습(PPO)으로 시작했지만, 실험을 거쳐 **"게임판 인식 + 탐색"** 이 실제 게임에서 가장 잘 동작한다는 결론에 도달했다.

## 결과 요약

| 단계 | 방법 | 결과 |
|---|---|---|
| v1 | PPO / DQN (stable-baselines3, 마스킹 없음) | 학습 4~5시간, 고득점 실패 |
| v2 | 행동 마스킹 + 배치 PPO | 정책 단독 110~114점 (탐욕 규칙 114점을 못 넘음) |
| v3 | AlphaZero식 (MCTS 자기대국) | MCTS 122~124점, 정책 단독은 여전히 탐욕 수준 |
| v4 | 롤아웃 탐색 (학습 없음) | 균등 보드 130점, 실제 보드 평균 130점 |
| **실전** | **화면 인식 + 롤아웃 탐색 + 실제 마우스 (`play.py`)** | **실제 게임 140 / 170점 (1분 3초)** |
| v5 | 시작 시 수 순서 미리 계산 (`--plan-time`, 빔 + 무작위 여러 판) | 실제 보드 시뮬레이션 평균 +8점 (아래 표) |
| v6 | numba 고속 탐색 (약 60배 빠름) + 120초 자동 계획 | 실제 납작한 사과 보드 5장 평균 **142.2** (v5 138.2), 둥근 사과 170 |

> 점수 = 한 판에서 지운 사과 수. "탐욕 규칙" = 가능한 수 중 사과를 가장 적게 지우는 수를 고르는 단순 규칙.

## 실행 방법

```bash
pip install -r requirements.txt

# 실제 게임 자동 플레이 (본인 PC, 브라우저에서 게임을 시작해 사과판이 보이게 한 뒤)
python play.py --dry-run     # 마우스는 안 움직이고 인식과 첫 수만 확인 (dry_run.png)
python play.py               # 실제 마우스로 플레이. 멈추기: 마우스를 화면 왼쪽 위 모서리로 / Ctrl+C

# 스크린샷 한 장 풀기
python solve_image.py assets/board_1.png

# 연구용: 학습과 평가
python train_az.py --minutes 15 --dist flat                       # AlphaZero식 학습 (GPU 권장)
python evaluate.py --ckpt models/az_flat.pt --mcts 64 --real flat  # 실제 스크린샷 보드로 평가
python evaluate.py --boards 1000 --dist flat                       # 기준선(무작위/탐욕) 비교
```

`play_web.py`는 Playwright로 브라우저를 직접 제어하는 버전이다 (좌표 배율 문제 없음, 커서는 화면에 보이지 않음).
게임 링크(`/play/...`)는 일회용이라, 열린 창에서 메인 페이지부터 직접 게임을 시작해야 한다.

## 동작 방식 (`play.py`)

매 수마다 다음을 반복한다.

1. **화면 캡처** (`mss`)
2. **게임판 찾기** (`vision.locate_grid`): 빨간 사과 픽셀을 행/열로 투영해 17×10 격자를 찾는다. 사과 꼭지(갈색)처럼 빨간 픽셀이 적은 구간은 버린다.
3. **숫자 인식** (`vision.read_board`): 칸마다 흰 숫자를 잘라 크기를 맞춘 뒤 숫자 1~9 템플릿과 비교한다 (범용 OCR 없음). 사과 디자인 두 종류(둥근/납작한)를 모두 지원한다.
4. **수 선택**
   - 시작할 때 `planner.plan_game`이 처음 보드로 여러 판을 미리 풀어, 가장 좋은 수 순서를 정한다. 이 게임은 결정적이라 계획한 순서를 그대로 두면 그 점수가 나온다.
     계획 시간은 자동: 남은 게임 시간 - (예상 수 × 한 수 실행 시간 0.9초) - 여유 6초. 보통 45~65초.
     무작위 탐욕 512판으로 빠르게 답을 확보한 뒤, 롤아웃 빔 서치(폭 2 → 폭 4를 시드를 바꿔 반복)로 개선한다. 예상 시간 안에 끝날 실행만 시작한다.
   - 화면이 계획과 어긋나면 `search.rollout_best_move`(모든 수를 둬 보고 탐욕으로 끝까지 진행해 비교)로 한 수씩 계산한다.
5. **드래그** (`pyautogui`): 누른 뒤 잠깐 멈추고 10단계로 나눠 이동. Windows 화면 배율(DPI)을 보정한다.
6. **검증**: 계획한 칸의 사과만 사라졌는지 확인한다. 효과가 끝날 때까지 기다리고, 예상 밖 변화가 있으면 다시 읽거나 멈춘다. 마지막 수 직후의 게임 종료 창도 구분한다. 모든 수는 `play_log.txt`에 기록된다.

인식 정확도: 스크린샷 10장 × 배율 0.7~3배(70가지) 중 69가지 100%.

## 실험 기록

### 1. 환경 재설계 (v1 → v2)
- v1 문제: 8,415개 행동 중 유효한 수는 약 0.65%뿐인데 마스킹이 없었다. 합이 9·11이면 보상을 주는 바람에 보드를 바꾸지 않고 보상만 반복해서 받는 구멍이 있었다. 관측 공간 크기 선언(10×13)도 실제(10×17)와 달랐다.
- v2 변경: 합이 10이고 네 변에 사과가 걸친 사각형만 허용하는 마스크를 넣었다. 보상은 지운 사과 수로, 종료는 "둘 수 없음"으로 바꿨다. torch 배치 환경에서 모든 사각형 합을 행렬곱 한 번으로 계산한다 (환경 약 10,000 스텝/초, CPU).
- 정책 헤드: 8,415개짜리 출력 대신 칸 점수 맵에서 "사각형 내부합 + 모서리 점수"로 로짓을 만든다.

### 2. PPO가 탐욕 규칙을 못 넘는 이유 (측정)
- 첫 수를 최적으로 바꾸면 최종 점수가 +13.7점 달라질 수 있다. 개선할 여지는 분명히 있었다.
- 하지만 보드마다 점수가 ±15.4점, 같은 보드를 확률적으로 다시 플레이해도 ±6.0점 흔들린다. 한 수의 효과(약 1점)가 운에 묻혀서 PPO 학습 신호가 너무 약했다.
- 이 게임은 처음 보드만 정해지면 이후에 운이 전혀 없다. 결과를 정확히 계산할 수 있는 시뮬레이터가 있으므로 모델 없는 강화학습보다 **탐색**이 맞는 도구다.

### 3. AlphaZero식 학습 (v3)
- MCTS 자기대국 → (방문 분포 또는 Gumbel식 Q 개선 정책, 남은 점수)로 학습 → 반복.
- MCTS는 120점을 넘었지만 탐색 횟수를 4배로 늘려도 +1.7점에 그쳤다. 가치망의 정확도가 상한을 정했다.
- 정책망 단독은 PPO, AZ(두 가지 정답), 롤아웃 모방학습 모두 탐욕 수준(약 114점)에서 멈췄다.

같은 균등 보드 100판, 탐욕 114.2점 기준:

| 방법 | 평균 | 계산 시간 |
|---|---|---|
| PPO 가치망 + 빔 서치 | 125.6 | 판당 1.2초 |
| AZ + MCTS 256회 (GPU 학습) | 124.3 | 판당 4.4초 |
| 롤아웃 탐색 (학습 없음) | 130.0 (50판) | 판당 6.5초 |

### 4. 실제 게임 보드 분석
실제 스크린샷 10장(`assets/board_1~10`)으로 분석했다. 사과 디자인이 다른 두 버전이 있다.

| | 둥근 사과 (4장) | 납작한 사과 (6장) |
|---|---|---|
| 숫자 합이 10의 배수 | 4/4 | 6/6 |
| 숫자 분포 | 작은 숫자가 많음 | 거의 균등 |
| 처음 둘 수 있는 수 (숫자를 섞은 보드) | 88 (67) | 54 (54) |
| 롤아웃 탐색 | 168 | 130 |

- 둥근 사과 버전은 **"빈 칸만 있는 사각형 안 2~3칸에 합 10을 채우는" 역순 생성**으로 통계를 재현할 수 있었다 (`--dist round`).
- 납작한 사과 버전은 균등 무작위 + 합 10의 배수에 가깝다 (`--dist flat`).
- 생성 보드로 학습한 AZ 모델은 생성 보드에서 탐욕보다 +6점 높았지만, **실제 보드에서는 탐욕과 비슷했다**. 반면 학습이 필요 없는 롤아웃 탐색은 실제 보드에서도 +8점으로 안정적이었다.

| 실제 납작한 사과 보드 | 탐욕 | 롤아웃 | MCTS 64 | MCTS 256 |
|---|---|---|---|---|
| 평균 (6장) | 121.7 | **130.0** | 120.8 | 121.5 |

### 5. 시작 시 미리 계산 (v5)
120초 중 약 60초만 쓰고 있었다. 게임이 결정적이므로 처음 보드로 남는 시간 동안 여러 판을 풀어 보고 최고 순서를 실행한다.

실제 보드에서 계획 시간 45초, 화면 시뮬레이터로 끝까지 실행한 결과:

| 보드 | 한 수씩 (기존) | 미리 계산 | 사용한 방법 |
|---|---|---|---|
| 5 | 100 | **115** | 빔 폭 2 |
| 6 | 142 | **155** | 무작위 1024판 |
| 8 | 128 | **132** | 빔 폭 4 |
| 9 | 140 | **146** | 빔 폭 4 |
| 10 | 128 | **141** | 빔 폭 4 |
| 3 (둥근 사과) | 164 | **170** | 무작위 512판 (5초) |

- 무작위 탐욕 여러 판: 512판에 약 4초. 2048판으로 늘려도 512판 대비 +2점 정도라 효율이 떨어진다.
- 롤아웃 빔 서치: 폭 4가 가장 효과적(평균 +13점). 다만 예산 안에 못 끝내고 끊기면 오히려 점수가 낮아져, 예상 시간으로 시작 여부를 정한다.
- 폭 8은 폭 4보다 낫지 않았다(114/147/136 vs 114/146/141). 대신 폭 4를 시드만 바꿔 여러 번 돌리면 조금 더 오른다(3회 최고 평균 +1.6점).
- 120초를 최대한 쓰는 자동 계획(보드별 42~64초 계획, 총 105~113초): 평균 138.2점. 고정 45초(137.8)보다 +0.4점이라, 지금 탐색 방식은 시간을 더 줘도 거의 포화 상태다.

### 탐욕 말고 다른 롤아웃 규칙 (실험)
롤아웃(끝까지 둬 보기)에 쓰는 규칙을 바꿔 봤다.

| 규칙 (단독으로 끝까지) | 생성 보드 200판 | 실제 보드 6장 | 속도 |
|---|---|---|---|
| 탐욕 (최소 제거) | 120.1 | 117.5 | 기준 |
| 개선 규칙: 탐욕 + 다른 수와 겹치는 정도 감점 + 8·9 가점 | 122.1 | 122.5 | 비슷 |
| 선택지 많이 남기기 (둔 뒤 남는 유효 수 최대) | 127.3 | 127.2 | 20배 느림 |

탐색에 넣었을 때 (실제 보드 5장 평균):

| 방법 | 평균 | 판당 시간 |
|---|---|---|
| 탐욕 롤아웃 빔 폭 4 | 137.6 | 약 25초 |
| 개선 규칙 롤아웃 빔 폭 4 | 138.0 | 약 39초 |
| 선택지 빔 (롤아웃 없음, 폭 50, λ=3) | 132.8 | 약 13초 |
| 여러 방법 조합 (120초 예산) | 136.8 | - |
| **탐욕 빔 폭 4, 시드만 바꿔 반복 (120초 예산, 기본값)** | **138.2** | - |

- 단독으로는 "선택지 많이 남기기"가 훨씬 강하지만, 롤아웃 안에서 쓰기엔 너무 느리다.
- 보드마다 이기는 방법이 달랐지만, 시간이 정해져 있으면 여러 방법을 나눠 돌리는 것보다 가장 강한 방법 하나를 반복하는 쪽이 나았다.
- 지금 구현(Python + torch)에서는 이 정도가 한계로 보인다. 더 오르려면 계산 자체를 빠르게 만들어(C/numba 등) 더 많이 탐색해야 한다.

### numba 속도 개선 (v6)
`applegame/fast.py`: 사각형을 키우다 합이 10을 넘으면 멈추는 가지치기 + 롤아웃 멀티코어 병렬.
- 유효 수 계산: 9,000여 개 게임 상태에서 torch 버전과 완전히 일치
- 탐욕 롤아웃: torch 배치 대비 1코어 20배, 병렬 100배 빠름. 롤아웃 빔 폭 4: 판당 25초 → 0.4초

빨라진 만큼 빔을 넓히고 여러 번 돌릴 수 있다 (실제 납작한 사과 보드 5장 평균):

| 방법 | 평균 | 판당 시간 |
|---|---|---|
| 빔 폭 4 | 138.0 | 0.4초 |
| 빔 폭 64 | 141.2 | 6초 |
| 빔 폭 512 | 141.6 | 44초 |
| 빔 폭 64 × 시드 6개 최고 | 142.2 | 38초 |
| **빔 폭 32 × 시드 12개 최고** | **142.8** | 37초 |
| "선택지 많이 남기기" 롤아웃 빔 폭 16 × 시드 3개 | 142.2 | 112초 (예산 초과) |

120초 게임 전체를 실제 드래그 속도로 흉내 낸 시뮬레이션 (자동 계획 시간 + 빔 16 → 빔 32 반복):

| 보드 | v5 (torch) | **v6 (numba)** | 전체 시간 |
|---|---|---|---|
| 5 | 117 | **118** | 112초 |
| 6 | 155 | **162** | 107초 |
| 8 | 132 | **136** | 110초 |
| 9 | 146 | **152** | 110초 |
| 10 | 141 | **143** | 111초 |
| 평균 | 138.2 | **142.2** | |
| 3 (둥근 사과) | 170 | 170 (계획 6초) | 80초 |

numba는 처음 실행할 때 컴파일에 시간이 걸리므로, `play.py`는 카운트다운 전에 미리 컴파일한다(`planner.warmup`). numba가 없으면 기존 torch 탐색으로 자동 전환된다.

### 6. 실제 게임 연결
- 화면 캡처 + OS 마우스 → 드래그가 반영되지 않아 드래그 방식을 바꿨다 (누른 뒤 멈춤, 단계별 이동). 고해상도 화면에서는 사과 꼭지 때문에 행이 20개로 잡히는 버그가 있어 고쳤다.
- Playwright 브라우저 제어(`play_web.py`)도 만들어 가짜 게임 페이지(`tools/mock_game.html`)로 배율 100/150/200%를 검증했다.
- 최종: 실제 게임에서 **140 / 170점, 58~59수, 약 1분**.

## 배운 것
1. **문제 정의가 알고리즘보다 먼저다.** v1의 실패 원인은 PPO냐 DQN이냐가 아니라 마스킹 없는 행동 공간과 보상의 구멍이었다.
2. **기준선부터 만든다.** "탐욕 114점"이라는 기준이 없었다면 PPO가 무엇을 배웠는지 판단할 수 없었다.
3. **실패도 측정한다.** "PPO가 안 된다"를 신호(1점) 대 운(±15점)으로 수치화하니 방향 전환의 근거가 생겼다.
4. **결과를 정확히 계산할 수 있으면 탐색이 강하다.** 학습된 가치망은 분포가 바뀌면 흔들리지만, 롤아웃은 흔들리지 않는다.
5. **학습 데이터 분포가 실제와 같은지 확인한다.** 균등 무작위 보드로 잰 점수(114, 130)는 실제 게임과 달랐고, 실제 보드 10장으로 생성 규칙을 역추정해야 했다.
6. **실전 연결이 절반이다.** 인식(해상도, 디자인 두 종류), 입력(DPI, 드래그 방식), 검증(애니메이션, 종료 창)에서 문제가 계속 나왔다. 단계마다 시뮬레이터를 만들어 검증하는 것이 효과적이었다.

| 파일 | 내용 |
|---|---|
| `applegame/env.py` | 배치 환경, 행동 마스크, 보드 생성기 (uniform / round / flat) |

| `applegame/fast.py` | numba 고속 버전: 유효 수 계산, 롤아웃, 롤아웃 빔 서치 |
